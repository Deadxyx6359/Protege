A fully local, offline AI assistant with a **knowledge lock system**. The
underlying model keeps all its pretrained capability; the application gates what
it is permitted to use. Topics start locked. You unlock them by teaching them.

The purpose is pedagogical: you learn by teaching. A lock that leaks defeats the
point, so the lock system is the highest-priority component and was built first.

**Quick start on this machine:** double-click the **Akira** shortcut on the
desktop. Everything below (model, CUDA runtime, vault configuration) is already
installed and wired up; first launch asks you to choose a PIN.

## The look

Purple on black, **pure white** text. Opens maximised.

**Why text looked low-res, and the actual fix.** It was never the typeface.
Windows renders a non-DPI-aware process at logical size and bitmap-stretches
it, so on a 125% display (this machine: 3440 physical pixels reported as 2752)
every glyph is resampled and arrives soft. Akira now declares per-monitor DPI
awareness *before Tk starts* -- `theme.enable_dpi_awareness()`, called from
`run.py` ahead of any Tk call -- and scales its own pixel geometry through
`theme.px()`. If text ever goes soft again, check that call still runs first.

Two font roles: **Segoe UI** for interface chrome, **Cascadia Mono** for chat,
the rain, and wordmarks. All-mono-everything reads like a screenshot of a
config file.

The chat is a **fixed-width reading column** with rain filling everything on
both sides, so a wider window buys more rain rather than longer, harder-to-read
lines. Rain columns are seeded across the full canvas height at startup:
falling from above the top takes 12-23 seconds to reach the bottom, which left
the field visibly empty for the first twenty seconds of every launch.

A lean **sidebar** carries navigation only -- five destinations, projects, and
a footer. Creation lives on a circular **+ button** bottom-right: new skill,
attach file, import file, unlock a topic. An earlier sidebar listed thirteen
rows, which is a menu bar wearing a sidebar's clothes. There is deliberately
**no menu bar**: Windows draws it natively, ignores Tk's colors, and rendered
as a bright white strip across an otherwise black window.

While the model works, a **pulsing indicator** names the current stage in plain
language -- "searching your notes", "checking the response" -- with an elapsed
clock, and after eight seconds adds why that phase is slow. A 40-second silence
is indistinguishable from a crash; a named phase with a running clock is a
system visibly doing its job.

Every dialog **sizes itself to its own contents** on open and sets a matching
minimum. `tests/test_dialog_geometry.py` measures required against actual for
all thirteen, so a button can never again end up below the fold.

Title bars are dark via DWM, and the app has its own tree icon (generated by
`tools/make_icon.py` -- a real multi-resolution `.ico`, no image library).

Blocked responses render in pink-red, the disabled-layer warning strip in amber
-- the two loud colors are reserved for the two things you must not skim.

(The original brief specified an untheme; the visual direction was a later,
deliberate override. The structural part survives: plain Tk widgets, no styling
libraries, no bitmap assets beyond the icon.)

## Keys

| | |
|---|---|
| `Enter` / `Shift+Enter` | send / newline |
| `Esc` | **stop the current generation** |
| `↑` (in an empty box) | bring back the last thing you sent |
| `Ctrl+R` | ask the last question again |
| `Ctrl+N` | new session |
| `Ctrl+K` | knowledge web |
| `Ctrl+,` | settings |

**Stop** matters more than the rest put together. A generation on a 24B takes
minutes, and there was previously no way to abandon one — the Send button
greyed out and the only escape was closing the window. It is now a Stop button
in the same place, and Escape.

Cancellation is cooperative, because a Python thread cannot be killed: the
token and stage callbacks raise, which unwinds llama.cpp's stream. Pressing
Stop while MAIN is streaming therefore aborts *before* the auditor — the slow
phase — is ever started. A turn already inside the auditor has to finish, and
its result is discarded on arrival rather than appearing minutes later.

Shortcuts are inert while a modal dialog has the grab, so `Ctrl+N` over the
Settings window cannot start a new session invisibly behind it.

## Skills you get for free

**Knowledge → Skills → Library** ships seven reviewed tools:

| | |
|---|---|
| `code_review` | static review of a Python file — mutable defaults, bare excepts, `== None`, over-long functions |
| `doc_outline` | heading tree, per-section word counts, reading time |
| `text_stats` | readability, overused words, over-long sentences |
| `data_table` | CSV or JSON into a markdown table |
| `json_tool` | validate, describe, reformat; pinpoints parse errors by line and column |
| `project_summary` | file and line counts, plus every TODO/FIXME left in a tree |
| `diff_files` | unified diff between two text files |

They obey the same rules the authoring path enforces on model-written skills:
standard library only, no network, no subprocess, results on stdout. Shipped
code gets no exemption.

Installing one copies its source into the project and **does not approve it**.
Approval stays digest-bound in the Skills window, because "it came with the
app" is exactly the reasoning that makes supply-chain trust invisible.

Each takes a file: put it in the **Arguments** box in the Skills window, or use
**File...** to pick one. The selected skill's own `usage:` line is shown beside
the box. Arguments come from you, never from the model -- approval covers a
skill's *code*, and letting MAIN choose what to point that code at would hand
it a general-purpose file reader nobody approved.

Every shipped skill is executed against real input in the test suite — a broken
tool in the library would burn the credibility of all of them.

## The knowledge web

**Sidebar → Knowledge web** draws what the model may know as a skill tree.
Topic ids cluster by their first underscore segment, so `python_basics` and
`python_loops` branch off a `python` hub; co-tagged topics get a faint dashed
cross-link. Unlocked topics glow filled purple, locked ones sit dark with a dim
outline -- territory that exists but has not been taught. Click a node to see
its provenance and note count, and to run the unlock or re-lock flow from there.

The hierarchy is a naming heuristic and is honest about it: it invents no
relationships beyond what your topic names and co-tagging already say. The
layout is deterministic, so the map holds still between openings -- a picture
that rearranges itself every time is useless for building a mental model.

## Browsing and editing the vault

**Sidebar → Browse vault** lists every note in the current project plus the
global ones, each marked with what the model can actually see:

```
[*] visible    [L] locked    [-] untagged    [!] unreadable
```

Select a note to edit its body and its `topics:` line, with the consequence
stated live as you type ("Locked: chemistry — invisible to the model until
unlocked"). That feedback is the reason this exists at all: the topics line is
what governs visibility, and editing it in an external editor gives you no
signal about whether the id you typed actually matched.

Projects are created, renamed and deleted from the same window. Deleting names
what is inside first ("Contains 12 note(s), 3 memory file(s)"), and refuses to
remove the last remaining project. Note and project deletes are irreversible.

Saving a note preserves the frontmatter Akira wrote — `kind`, `session`,
provenance — rather than flattening it to just the topic list.

## Files in, files out

- **Attach** (the **+** button → Attach file): puts a text file's contents into
  the current conversation. Session-scoped, never written to the vault, and
  budgeted like every other context section.
- **Import into vault** (the **+** button → Import file): copies a text file in as a topic-tagged
  markdown note. Permanent, and governed by the same visibility rules as any
  note -- tagged with a locked topic, it stays invisible until you unlock it,
  which is exactly how unlock source notes usually arrive.
- **Import a document** (the **+** button → Import a document): reads a **PDF**,
  **Word .docx**, Markdown or text file, splits it at its own headings, and
  proposes *one topic per section* -- `dc_ohms_law`, `dc_kirchhoff`,
  `dc_thevenin` from one handout, instead of one blob you would have to divide
  by hand. Every id is editable and every section can be dropped before
  anything is written.

  The importer stocks the shelves; it does not read the books. Sections arrive
  **locked**, and each still has to be unlocked by explaining it. A convenience
  that skipped that would be a convenience around the point of the program.

  PDF text is recovered without any third-party library (`akira/pdftext.py`):
  object streams are expanded, Flate streams inflated, `/ToUnicode` CMaps
  applied, and word gaps reconstructed from kerning or glyph spacing. Headings
  are inferred from type size, since a PDF records no structure at all. A
  **scanned** PDF has no text to find and says so rather than importing
  nothing.

Attached content is user-supplied and is not gated on the way in; the model's
*replies about it* still pass tripwires and the auditor, so an attachment
cannot launder locked knowledge out of the model.

## What it actually does

Everything is locked at first launch — ethics, literature and mathematics
exactly like geography. There is no "unlock all", and no seeded topic list,
because seeding one would be the application deciding what you don't have to
teach.

To unlock a topic you write notes about it in your vault, then run an unlock:
the model is shown your notes, summarizes them, generates its own comprehension
questions, and answers them. You read the demonstration and approve or reject
it. On approval the topic enters the manifest with provenance — which notes, and
when.

Unlocks are reversible. Re-locking hides every note carrying that topic,
including memory notes the model wrote in past sessions.

---

## Teaching a topic — the only thing that unlocks

**Explaining something in the chat does not teach it.** Nothing said in a
conversation can widen what the model may use; that is the security property,
not an oversight. Otherwise "I hereby teach you chemistry" would be a one-line
bypass.

The flow that does work:

1. Write a note in the vault tagged `topics: [your_topic]` — Sidebar →
   **Browse vault**, or **Import into vault**, or just create the `.md` file.
2. Sidebar → **Unlock a topic**, pick the topic and that note.
3. The model reads *your note*, summarizes it, generates its own comprehension
   questions, and answers them.
4. You approve. The topic enters the manifest with provenance.

When a reply comes back `[LOCKED: something]`, the chat now says so and offers
a **teach `something` now** link that opens the unlock flow with the topic
pre-filled.

Note the distinction the lock system draws, which is subtler than it looks: in
testing, "Do you understand?" → **"Yes."** passed, because a bare yes carries
no subject knowledge, while "tell me what you learned" was **blocked**, because
recounting it would. Same topic, different information content.

## Two modes

**Akira mode** is the default and the point of the program: the model answers
only from what you have taught it.

**Everyday mode** (Sidebar → **Everyday mode**) stands the lock down and gives
you an ordinary local assistant answering from its full training. It exists
because the two jobs are genuinely different — a study aid that makes you earn
every topic is the right tool for coursework and the wrong one for "what is the
syntax for a bash case statement".

What it does *not* do is unlock anything:

- `unlocked_topics` is untouched, so switching back restores the lock exactly.
  The knowledge web and the topic manager keep showing what you have actually
  taught, in both modes.
- The flag is runtime-only. It appears in neither `to_json` nor `from_json`, so
  it cannot be set by editing `manifest.json`, and it cannot survive a reload.
- A banner sits across the top of the window and the status bar reads
  **EVERYDAY MODE** for as long as it is on. The whole difference between the
  modes is invisible in the answers themselves — a reply with no
  `[LOCKED: ...]` marker looks identical whether the topic was taught or the
  constraint was off — so it is stated where it cannot be missed.
- Retrieval stays **on**. It is your vault; everyday mode should not be worse
  at your own notes than Akira mode is.

## Review — unlocks that age

A topic unlocked once used to stay unlocked forever, and nothing ever asked
whether the material had held. For a program whose purpose is pedagogical that
is the shape of a permission system, not of learning.

Topics now age. The clock is the manifest's own history — the most recent
unlock or review of a topic is when it was last demonstrated — so there is no
new file to corrupt and every topic ever unlocked already has a timestamp.

- Due topics carry an amber **!** in the knowledge web and are listed once at
  launch. They are still unlocked; nothing is taken away.
- **Knowledge → Review...** re-runs the same demonstration against your notes as
  they stand now. Passing resets the clock and grants nothing new. Failing
  costs nothing — the topic stays unlocked and stays due, and the fix is to
  rewrite the note.
- Automatic re-locking exists in **Settings → Review** and is **off** by
  default. When on it waits for the review interval *and* a grace period, so
  falling due and losing access never happen on the same morning. Silently
  withdrawing access to something you did learn is worse than letting a stale
  unlock stand. Set the interval to 0 to switch the feature off entirely.

## Session history

Transcripts are deleted once consolidation is confirmed. That is the default
and it stays the default: the safe behaviour for a local assistant is not to
accumulate a searchable record of everything you have ever said.

**Settings → Memory → Keep transcripts** changes it. Transcripts then move to
`memory/archive/` instead of being deleted, and **Sidebar → History** searches
them. Both places a transcript can die — session end and the holding sweep —
go through one function, so the setting cannot be honoured in one and forgotten
in the other.

Archived transcripts are never fed back to the model. A transcript contains
drafts the gate blocked; indexing it for retrieval would hand back exactly what
was stopped.

## The five layers

All active simultaneously. They fail differently on purpose: Layers 2 and 5 are
both language models being asked to be careful, and they fail in correlated
ways. Layer 4 has no model in it at all.

| Layer | What it is | Honest assessment |
|---|---|---|
| **1. Manifest** | `vault/.protege/manifest.json` — the single source of truth | Reliable. It's a file. |
| **2. Lock directive** | Instructs MAIN, with a fixed `[LOCKED: topic]` decline string | **Weakest layer. It will leak.** Exists to reduce load on the layers below. |
| **3. Scoped retrieval** | BM25 over the vault; locked-topic notes are invisible | Strong for what it covers — but it only controls what goes *in*. |
| **4. Tripwires** | Deterministic keyword/regex checks over MAIN's output | Fast, dumb, catches obvious leakage. **Produces false positives by design.** |
| **5. Auditor** | A second model returns `VERDICT: PASS` or `VERDICT: BLOCK` | A 3B-class model with both false positives and false negatives. **A meaningful filter, not a guarantee.** |

**Fail closed.** Any error, timeout, ambiguity, or component failure blocks the
response rather than passing it. There is no code path where an exception
produces text on screen, and no setting — including auditor strictness — that
makes any layer fail open.

Three visibility rules govern retrieval, all fail-closed:

1. An **untagged** note is invisible. Otherwise the lock would be opt-in: write
   about a locked subject, omit the frontmatter, done.
2. A note is visible only when **every** topic it carries is unlocked. Not any.
3. A note that **fails to parse** is invisible. Unknown topics are treated as
   locked.

## Hard constraints

1. **No network access, ever.** No telemetry, update checks, analytics, CDN
   fonts, or remote assets. All inference is local. Dependencies are pinned
   exactly.
2. **No socket is ever opened.** llama.cpp is bound in-process via ctypes. This
   is why Ollama and LM Studio are ruled out — they are HTTP servers.
3. **Fail closed**, everywhere.
4. **No file or shell access at the default trust tier.**
5. Every dependency is justified in a comment in `requirements.txt`.

`verify_offline.py` proves point 1 statically. It walks the transitive import
graph from the entry points and fails on any reachable networking module. It
distinguishes module-level imports (which execute) from function-local ones
(which execute only if called) — `llama_cpp` ships an unused FastAPI server and
a HuggingFace downloader, and flagging those on every clean install would train
you to ignore the check.

```bash
python verify_offline.py
```

## Requirements

- **Python 3.11+** (3.12 tested)
- **GPU:** this machine has an RTX 3060 **Laptop** GPU with **6GB** VRAM (not
  the 12GB desktop card the original brief assumed).
- **System RAM: 15.7GB total on this machine**, and it is the binding
  constraint. 32GB recommended for anything larger.

### What is actually installed here

**Mistral Small 3.2 24B Instruct (2506), Q4_K_M — 13.35GB**, shared between
MAIN and AUDITOR so it loads once.

Measured on this box, not estimated:

| `n_gpu_layers` | VRAM | System RAM | Speed |
|---|---|---|---|
| 14 | 5355 MiB | **15.6 / 15.7 GB** — at the edge | 2.09 tok/s |
| **20 (configured)** | 5943 MiB | 14.6 GB | **2.19 tok/s** |

Counter-intuitively, pushing *more* onto the GPU lowers system-RAM pressure and
is slightly faster — llama.cpp keeps non-offloaded weights in host memory, so
offloading fewer layers is what starves the machine. The dGPU idles at 0 MiB
here (it is not driving the display), so that VRAM is genuinely free.

**A real turn is ~40s**: generation plus the auditor pass, which runs on every
single message. At 2.19 tok/s a maximum-length reply (700 tokens) takes about
five minutes — if it looks hung, that is what is happening. Lower **Max
response tokens** in Settings → Models if that bites.

Earlier candidates, since the reasoning may be useful if you swap again:
Ministral 8B (the brief's model, weaker), Qwen3 8B, and Qwen3 14B (~9GB, also
comfortable, but Qwen3 emits `<think>` reasoning blocks that have to be
filtered — see `models/think_filter.py`, which stays in place and is a no-op
for Mistral).

### Models

Configured: **Qwen3 14B, Q4_K_M** (Apache 2.0), serving as both MAIN and
AUDITOR. Akira detects identical paths and loads the file once, so the
auditor costs no extra memory and reads MAIN's output in exactly the same
dialect — the matched-tokenizer property the brief wanted, for free.

```bash
curl -L -o models/Qwen3-14B-Q4_K_M.gguf \
  https://huggingface.co/Qwen/Qwen3-14B-GGUF/resolve/main/Qwen3-14B-Q4_K_M.gguf
```

**14B is the ceiling on this machine, and RAM sets it — not patience.** With
15.7GB of system RAM, a 24B (~14GB) leaves Windows nothing and page-thrashes;
30B and 32B (~18–20GB) do not fit at all. If you add RAM, the model to jump to
is Qwen3 30B-A3B: a mixture-of-experts with only ~3B parameters active per
token, so it runs far faster than a dense model of similar quality.

**Measured on this hardware** (RTX 3060 Laptop, 6GB VRAM):

| `n_gpu_layers` | VRAM used | Verdict |
|---|---|---|
| 30 | 5971 / 6144 MiB | No headroom left for the KV cache — rejected |
| **24** | **5787 / 6144 MiB** | **Configured.** ~2.4 tok/s, auditor pass ~2s |

A 700-token answer therefore takes roughly five minutes, plus a couple of
seconds for the audit. If that is too slow, `models/Qwen3-8B-Q4_K_M.gguf` is
still on disk and runs fully on the GPU — select it in Settings → Models and
set GPU layers back to `-1`.

> **Qwen3 thinks out loud**, emitting reasoning between `<think>` tags. Akira
> disables that at the source for Qwen3 files and filters the tags out of the
> token stream regardless (`akira/models/think_filter.py`). Not cosmetic: the
> auditor's grammar is two lines, so a reasoning preamble around
> `VERDICT: PASS` parses as malformed — which blocks *every* response. An
> unfiltered stream presents as a totally broken application.

> **Corrections to the original brief**, for the record: there is no "Ministral
> 3" family; Ministral 8B/3B 2410 are Mistral Research License, not Apache 2.0;
> and Ministral 3B has no GGUF because its weights were never published. The
> Ministral 8B build is still in `models/` and selectable in Settings → Models.

A **call** is hands-free: Akira listens, sends what you say to the chat, and
reads the reply as it is written. The microphone is open only during a call you
started, and mute closes it. There is no wake word. On speakers Akira waits
until it has finished speaking before it listens again; with headphones you can
let yourself interrupt it by talking.

### Run

The **Akira** desktop shortcut launches the app against your Obsidian vault
with no console window. `Akira (console).bat` in this directory does the
same with a console attached, for reading errors when something misbehaves.

`run.py` lives in this project directory, not in your vault — the two are
separate on purpose, so Obsidian never indexes the application and your vault
stays portable. Run it by absolute path from anywhere:

```bash
python "C:\path\to\akira\run.py" --vault "C:\path\to\your\Obsidian Vault"
```

Or `cd` into the project first:

```bash
cd "C:\path\to\akira"; python run.py --vault "C:\path\to\your\Obsidian Vault"
```

Set `AKIRA_VAULT` to skip the `--vault` argument. To validate configuration
without starting the UI:

```bash
python "C:\path\to\akira\run.py" --vault "C:\path\to\vault" --check
```

**Before you install a model**, the app still starts: you get the PIN dialog and
the main window, and every menu is explorable. Sending a message refuses with
"No inference library" until `llama-cpp-python` and a GGUF are in place.
Akira will not substitute a placeholder model — a fake model would sail
through the auditor, and a lock system validated against one proves nothing.

If you use Obsidian on the same vault: **disable Sync and all community
plugins.** Akira reads and writes the markdown directly and never touches
Obsidian's state, but a sync client will happily upload the vault Akira is
built to keep local.

## The auditor is the slow part, and it has to be

Measured on this machine (Mistral Small 24B Q4_K_M, `n_gpu_layers=20`), one
turn splits roughly:

| | |
|---|---|
| MAIN draft | ~27 s for 55 tokens (2.1 tok/s) |
| AUDITOR verdict | ~7 s median, 5–20 s, for **6 tokens** |

The auditor emits almost nothing and still costs a third of the turn, because
the cost is *prefill*: it has to read the prompt plus the whole draft — about
600 tokens — before it can say `VERDICT: PASS`. Shrinking `max_tokens` does
nothing; the output was never the expensive part.

**The obvious fix does not work.** A dedicated small auditor was tried:
Qwen2.5-1.5B-Instruct Q4_K_M, same prompts, same ten cases.

| | 1.5 B | 24 B |
|---|---|---|
| correct | **5 / 10** | 9 / 10 |
| per verdict | 0.1 s | 9.2 s mean, 7.2 s median |
| failure mode | **blocks everything** | one false block |

The 1.5B is two hundred times faster and unusable. It never emitted PASS —
not for unlocked-topic answers, not even for a bare `[LOCKED: geography]`
decline. In a fail-closed pipeline an auditor that always blocks is an
application that never answers. Speed alone would have said ship it; that is
why the benchmark scores accuracy.

So the shared 24B stays. The latency is the price of the gate being worth
anything, and the honest lever is a smaller MAIN, not a smaller auditor.

**One finding worth acting on.** The 24B's single miss was Ohm's law under the
unlocked topic `dc_basics` — correct material, blocked. The auditor is told
`<topic> (and everything within it)` and nothing else, so a vague topic name
fails in *both* directions: `programming_languages` was broad enough to let
Java through, and `dc_basics` was vague enough to keep Ohm's law out. Topic
names are the whole interface to Layer 5. Name them after what you could
demonstrate, not after the field.

## Security — read this part

### The PIN is an access convenience, not encryption

It is stored as a salted argon2id hash and never in plaintext. It stops someone
opening Akira on your unlocked machine.

**It protects nothing on disk.** Your vault is plain markdown and JSON. Anyone
with filesystem access can read every note, every transcript, and the manifest
itself, PIN or no PIN. A 4-digit numeric PIN is also brute-forceable in minutes
against the stored hash by anyone who has that file.

**Use full-disk encryption.** BitLocker on Windows, LUKS on Linux, FileVault on
macOS. That is the control that actually protects the vault at rest. For a
second layer you can keep the vault in an [`age`](https://github.com/FiloSottile/age)-encrypted
archive and unpack it only while working.

### Block egress at the OS level

Akira reaches the network through one door, `akira/core/net/client.py`, and
only to sites you allow with the *Fetch web pages* permission: https only, never
to this computer or your local network, capped in size and time, and recorded
in the activity log. A runtime guard raises on every other outbound connect,
DNS lookup and non-loopback bind, and `verify_offline.py` proves that no other
module can reach the network.

The interface is held to the same door. Qt, which draws it, can fetch pictures,
fonts and pages by itself, in C++, where neither check would see it. So every
QML engine Akira makes refuses the network outright, `verify_offline.py`
checks that it does, and pictures in replies are shown as links rather than
loaded.

**Neither is as strong as a firewall rule.** Both are application-level controls
running inside the process they protect; native code can call the OS directly
via ctypes without touching anything they guard. Network-level blocking is
strictly stronger.

Windows, elevated PowerShell:

```powershell
New-NetFirewallRule -DisplayName "Block Akira egress" -Direction Outbound -Program "C:\Users\you\AppData\Local\Programs\Python\Python312\python.exe" -Action Block
```

That blocks *all* Python egress, which is blunt. A dedicated virtualenv
interpreter for Akira makes the rule precise.

With the rule in place Akira still works; only fetching pages fails, and it
says the site could not be reached. Leave the interpreter unblocked only if you
want pages from the sites you allow. A firewall rule matches addresses, not site
names, so the list of sites is enforced inside Akira, by the chokepoint, not
by the rule.

### Audit log

Off by default. Enabling it in **Settings → Security** appends one line per gate
decision to `vault/.protege/protege.log`: which layer fired, on which topic, how
long it took.

**Metadata only — never the text.** A log holding blocked drafts would be a
plaintext copy of exactly what the lock system withheld, sitting in the vault
where retrieval could later find it.

### Trust tiers

A single integer in the manifest, changed only in Settings with PIN
confirmation. Tiers gate **the model**, not Akira itself — the application
always reads its own config, because the manifest is what defines the gate.

| Tier | Model gets |
|---|---|
| **0** (default) | Conversation only. No filesystem, no retrieval, **no memory writes at all**. |
| **1** | Read-only vault. Retrieval works. Memory writes user-pinned only. |
| **2** | Read/write within the vault. Model-proposed memory enabled. Skills may run. |
| **3** | Vault plus a user-specified allowlist of external directories. |

**No tier grants network access.** That is enforced structurally, not by a
permission check.

Every path is resolved and validated against permitted roots before any
operation. Traversal is blocked at all tiers, along with symlinks that escape,
NTFS alternate data streams, and reserved Windows device names.

### Skills

MAIN can author Python skills. They are **written to disk and never
auto-executed**. Running one requires explicit per-skill approval bound to the
file's SHA-256 — approving covers *that exact content*, so if the model rewrites
the file the approval is void.

Approved skills run in a subprocess with the network guard installed before
their code compiles, a scrubbed environment, an isolated working directory, a
timeout, and output caps.

**Knowledge → Skills** is where you author, read, approve, run, and revoke them.
The approval dialog shows the digest, because "approved" and "approved for the
version I actually read" are different claims and only the second is worth
anything.

**A Python subprocess is not a security boundary.** Code running as your user
can read your files and call the OS directly. What protects you is that nothing
runs without you approving it, not the subprocess. Treat approving a skill
exactly like running a script someone sent you.

## Personality

Ten shipped traits: directness, verbosity, formality, warmth, humor, curiosity,
pedagogical mode, confidence signaling, technical density, proactivity. All
default to neutral, so a fresh install contributes **zero** personality text.

Each trait has a 0–100 slider and five descriptive bands covering 0–20, 21–40,
41–60, 61–80, 81–100. **The slider selects a band; the band's prose enters the
system prompt. The number never does** — an 8B model does not reliably
distinguish "formality: 60" from "formality: 70".

- Traits at neutral are **not injected at all**.
- At most **8 traits** are active; the UI warns beyond that. Past about eight
  competing behavioral instructions a small model starts dropping them
  unpredictably.
- Custom traits require **you** to write all five bands. Akira cannot generate
  meaningful descriptions for a trait it has never seen, and plausible-sounding
  invented ones would be worse than asking.
- Shipped traits are fully editable, band text included.
- **Live preview** regenerates the last response under the current sliders
  without committing them. This is how the sliders actually get calibrated.

## Context budget

Priority order. Lower items are truncated first:

1. **Lock directive + unlocked topic list — never truncated**
2. Personality bands (active traits only)
3. `project.md`
4. Retrieved notes (relevance-ranked)
5. Live session memory
6. Recent conversation turns

The directive is allocated before anything else and is assembled **last** in the
system prompt. If personality and the directive competed on equal terms, lock
compliance would degrade in proportion to how much personality you had
configured — a security control whose strength depends on a cosmetic setting is
not a control.

Nothing is dropped silently. Truncations appear in the status line and in
**Session → Assembled prompt**, which shows the exact text MAIN received plus
the per-section token breakdown.

## Memory

Three tiers with different lifetimes:

```
vault/
  .protege/            manifest, settings, personality, tripwires, plugins
  projects/
    <project-name>/
      project.md       durable context — always loaded
      notes/           permanent knowledge notes (topic-tagged)
      memory/
        live/          active session scratch
        pending/       consolidated but unconfirmed
        holding/       transcripts awaiting deletion
      skills/
  global/
    notes/             cross-project knowledge
```

Two write mechanisms, both required: the model calls `remember(content, topic,
importance)`, and you can pin any message directly. An 8B model is unreliable at
noticing what matters, which is why the second exists.

**Every memory write passes tripwires and the auditor before it reaches disk.**
Memory is a leak vector: anything written into the vault becomes retrievable
later, at which point it is just a note. If MAIN wrote locked content there, the
gate would be bypassed by the model's own notes.

At session end, MAIN merges the live file into durable notes, deduplicating
against what exists. Output goes to `memory/pending/`, **not** to `notes/`, and
pending notes are not retrievable — otherwise unreviewed model output would
influence answers before anyone read it.

**The transcript moves to a holding area, not the bin.** Consolidation is done
by an 8B model and will sometimes produce lossy or wrong notes. If the transcript
is gone when you notice next week, the source is unrecoverable. Default 7 days,
configurable, with an immediate-delete option. Deletion is irreversible and the
UI says so before doing it.

## Extensibility

- **Plugin directory** at `vault/.protege/plugins/` with a documented interface
  in `akira/plugins.py`. Plugins get a `PluginContext` that hands out
  `generate_checked` — never a raw model backend — so extensions inherit gating
  by construction rather than by remembering to ask.
- Plugins are **never auto-loaded**. Each must be explicitly enabled in
  **Settings → Plugins** and its SHA-256 must match what was approved.
  `verify_offline.py` cannot vouch for a file that did not exist when it ran,
  and the check reports that exemption on every run rather than hiding it.
  "Write example plugin" drops a working, disabled example into the directory.
- **The base model is a replaceable component — assume it will be replaced.**
  Nothing above `akira/models/` knows llama.cpp exists.

## Development

```bash
python -m pytest          # 908 tests
python verify_offline.py  # networking scan
python tools/make_icon.py # regenerate the app icon
```

`tests/test_ui_flows.py`, `test_settings_roundtrip.py` and
`test_vault_browser.py` drive the real widgets the way a person does — move a
slider, press Save, close, reopen — and then check the file on disk. They exist
because unit tests on the underlying dataclasses all passed while the Settings
window was still losing personality edits: the bug lived in the wiring between
components that were each individually correct.

The test suite is weighted toward the lock system. `tests/test_lock_adversarial.py`
scripts MAIN to actually leak — jailbreaks, roleplay framing, translation
requests, fake auditor verdicts — and asserts the pipeline withholds it every
time. `tests/test_memory.py` does the same for writes smuggled into the vault. A
lock-system test suite built on a well-behaved model measures the model's
manners, not the lock.

One test asserts that disabling every layer **does** let a leak through. That is
deliberate: the toggles are a real feature with a real consequence, and the UI's
warning strip is calibrated against exactly that behavior.

## Scope note

Ethics, morality, and literature are locked topics at first launch, gated
identically to geography or mathematics. This is intentional — it is the
mechanism by which you teach them.

Akira does not attempt to modify or strip the base model's trained
dispositions. That isn't achievable through prompting and would produce an
unreliable student rather than a blank one. **The lock system is behavioral
gating. The weights are untouched.**
